# Spec：一窗一灯 — 多终端会话隔离

> 状态：待确认（seams 与验收口径）
> 日期：2026-11-26
> 关联分支：worktree-feat/per-window-lamp
> 前置门禁：`probe.ps1` 双终端实测（尚未取得用户输出）

## Problem Statement

我在一个项目里并行改多个 bug，会开多个终端各跑一个 CodeBuddy 会话。现在的红绿灯**按项目名**做键：一个项目只有一个灯、一个守护进程、一个状态文件。

于是切换到我正在处理的那个终端时，头顶没有灯；灯停在我没在看的那个终端上，而且它显示的是"最近活动"那个会话的状态——不是我想看的那个终端。更糟的是关掉任意一个终端会把共用的灯一起杀掉。结果灯从"抬头就能判断"退化成"完全不可信"，我干脆不看它了。

## Solution

一个**终端窗口**一盏灯，灯贴在该窗口下方，只反映该窗口内会话的状态；同项目开多个终端互不干扰，关掉一个不影响另一个。

同一个窗口里的多个标签页共享一个窗口句柄，物理上只有一块屏，所以它们聚合到这一盏灯上，角标显示 `·N`（N = 不同会话数）；灯的主要标签取优先级最高那条会话的项目名。

任何解析不出窗口的会话都不静默：落到一台机器一个的降级灯上，标 `?`，并在下一条提示时自动重试归窗。

## User Stories

1. 作为同时改多个 bug 的开发者，我想每个终端都有自己的一盏灯，这样我抬头看哪个终端就知道那个会话在干什么。
2. 作为同时改多个 bug 的开发者，我想灯贴在我正在处理的那个终端上，而不是最近活动的那个。
3. 作为同时改多个 bug 的开发者，我想两个终端的状态互不覆盖，这样一个终端失败不会把另一个显示成失败。
4. 作为同时改多个 bug 的开发者，我想关掉一个终端时另一盏灯不受影响。
5. 作为同时改多个 bug 的开发者，我想强杀终端（任务管理器结束进程/直接关窗口）后灯能自己消失，而不是留一盏孤儿灯。
6. 作为同时改多个 bug 的开发者，我想灯被误杀后能在下一次提交提示时自动回来。
7. 作为同时改多个 bug 的开发者，我想 `/clear` 时灯不闪、不重建、不换位，只是回到空闲。
8. 作为同时改多个 bug 的开发者，我想同一窗口的两个标签页合成一盏灯并显示 `·2`，而不是在同一块屏上堆两盏分不清主人的灯。
9. 作为同时改多个 bug 的开发者，我想 Windows Terminal 把标签页拖成新窗口后，灯在下一条提示时跟到新窗口。
10. 作为同时改多个 bug 的开发者，我想升级到新版本后不用手工清理旧计划任务和旧状态文件。
11. 作为同时改多个 bug 的开发者，我想重复安装/升级后不会出现重复灯。
12. 作为同时改多个 bug 的开发者，我想灯启动失败时（解析不到窗口）能看见一个带 `?` 的降级灯，而不是什么都没有。
13. 作为同时改多个 bug 的开发者，我想降级灯在会话恢复归窗后自己消失。
14. 作为用户，我想灯不抢焦点、不点亮任务栏图标（保持现状）。
15. 作为用户，我想灯跟随终端最小化而隐藏、还原而显示（保持现状）。
16. 作为用户，我想在 Windows Terminal、经典控制台（conhost）、Git Bash（mintty）之间行为一致，已知不支持的终端要在支持矩阵里写清楚。
17. 作为用户，我想同一秒内启动两个终端也不会出现两盏灯叠在同一个窗口上。
18. 作为用户，我想灯被手动结束进程后，计划任务不会残留。
19. 作为维护者，我想状态与绑定的写入在并发下不互相破坏，不需要文件锁。
20. 作为维护者，我想进程 PID 被系统复用时不会把新进程认成旧会话（创建时间必须匹配）。
21. 作为维护者，我想窗口句柄被复用时不会把灯贴到错误的窗口（锚 + 非篡改 + 活跃绑定三重判定）。
22. 作为维护者，我想高频 hook 事件（每次工具调用）不启动额外进程、不产生控制台闪烁。
23. 作为维护者，我想解析逻辑只有一份实现，源码版与 EXE 发布版行为一致。
24. 作为维护者，我想把所有 ps1 调用统一带 `-NoProfile -ExecutionPolicy Bypass`，避免用户机执行策略导致静默失效。
25. 作为维护者，我想发布包里自带解析脚本，解压即用不需要 Python。
26. 作为维护者，我想有单测覆盖键隔离、`/clear` 复用、PID 转世、GC 这些纯文件逻辑，不必真的开两个终端。
27. 作为维护者，我想有两条手工验收：两个终端各自只有自己的灯；强杀一个终端后另一盏无恙且死灯在一个 tick 内自灭。
28. 作为维护者，我想旧的项目级状态文件、PID 文件、计划任务在首次运行时被一次性清掉，且不误删新格式资产。
29. 作为维护者，我想 README 的支持矩阵与降级行为写清楚，用户不用猜。
30. 作为维护者，我想这次升级是破坏式的，不需要维护新旧两套键并存。

## Implementation Decisions

### 三层键模型（核心）

系统拆成三层，每层用各自的天然键，任何一层都不借用另一层的键：

- **身份层**：键 = CodeBuddy 进程 PID，值 = `<pid>.state`。必须同时记录并校验进程创建时间（FILETIME），PID 复用视为不同身份。状态聚合优先级（waiting > failure > thinking > running > success > idle）原样保留在这一层。
- **绑定层**：键 = hook payload 的 `session_id`，值 = `<session_id>.bind`。文件内容：`session_id / pid / creation_ft / hwnd / hwnd_owner_pid / hwnd_owner_ft / project / cwd / updated / degraded`。**身份字段（pid、creation_ft）写入后不可变，只有 hwnd 可刷新。**
- **project 是标签，不是键**：取主工作区根目录名（git common dir 的父目录），worktree 里回退到主仓库名而不是 worktree 目录名；非 git 目录才用 cwd basename。`cwd` 单独记录会话真实目录，二者不得混用。
- **显示层**：键 = 终端窗口 hwnd（十进制），值 = `w<hwnd>.win` 锚文件 + `traffic-light-w<hwnd>` 计划任务 + 一个 drawer 进程。一个 hwnd 恒等于一盏灯。

### 解析（唯一真相）

- 新的 PowerShell 解析器是 hwnd 的唯一来源；Python 侧不再自行发现终端，只看锚/绑定里传入的 hwnd。
- 父链只用于认"我是哪个 codebuddy 进程"（node.exe 且命令行含 codebuddy，排除 conpty/node-pty 类瞬时进程），必须一次 CIM 全量快照在内存里走完，不做逐层查询。
- hwnd 必须靠 attach-console 获取：短命解析进程内 `FreeConsole → AttachConsole(目标 pid) → GetConsoleWindow`；若得到 `PseudoConsoleWindow` 或零尺寸，取 `GW_OWNER`；再用 `IsWindow + IsWindowVisible + rect ≥ 50×50` 验收。探针实测该路径在 Windows Terminal（ConPTY）下有效，父链上溯拿不到窗口。
- attach 只在短命解析进程里发生，drawer 永不 attach（它没有控制台，attach 会挂上一个甚至闪窗）。
- 解析失败不静默：写 `degraded=1` 的绑定（pid 仍可用），进入降级灯。

### 写入与并发

- 所有文件写入用"同目录临时文件 + 重命名"原子替换，不用锁。
- 同一 pid 在 `/clear` 后会拥有新的 session_id：SessionStart 写新绑定前，删掉同 pid 的旧绑定文件，O(1) 无残留。
- 状态写入保持纯 shell（一次 `printf`），每次事件只多读一次自己的绑定文件；**PostToolUse 绝不启动解析器**。

### 灯的生命周期

- 抢窗用 `FileMode.CreateNew` 原子独占：赢者创建锚、拉 drawer；输者等待 500ms 复查锚仍新鲜才离开，复查失败重抢一次，仍失败则降级。
- 锚即心跳：drawer 每 tick 显式刷新锚的修改时间（不依赖"写了内容 mtime 自动更新"）。判定死：修改时间超过 3 tick 宽限（≥3 倍 tick），或连续两次读到 stale。
- 锚内带实例 nonce：drawer 每 tick 先验 nonce 再渲染，nonce 被替换即视为被取代，静默退出且不删除新锚。防止"被判死的旧 drawer 醒来刷 mtime 造成双灯"。
- 杀灯的唯一路径是 drawer 自检：窗口句柄失效、owner（pid+创建时间）不匹配、或本窗零活 pid 持续 2–3 tick → 自行注销计划任务、删自己的锚与 PID 文件后退出。
- SessionEnd 不杀灯、不删绑定，只把状态置 `ended`；`ended` 且 pid 仍活 → 按 idle 渲染，避免 `/clear` 的 End→Start 间隙闪一下。
- 绑定 TTL 60s，只在低频事件（SessionStart、UserPromptSubmit）检查并触发重解析；PostToolUse 只读现值。TTL 过期只降级 hwnd，不作废 pid，保证状态永远有处可写。

### 窗口层聚合

- drawer 只读 hwnd 匹配的绑定，按 pid 去重后聚合；`·N` 数的是不同 pid，不是绑定行数；N=1 时不显示角标。
- 主标签取优先级最高那条会话的项目名。
- 同窗跨项目也聚合（一个窗口一块屏）。

### 降级灯

- 全机器一个，固定键 `degraded`，聚合所有 `degraded=1` 的绑定，标签 `<项目> ?`，无 owner、自由置顶不抢焦点。
- 每 tick 扫绑定，已无失败会话即自灭。

### 迁移与 GC

- 破坏式升级，不保留项目键路径。
- 计划任务：`traffic-light-w<数字>` 是新格式，存活与否只看锚是否存在且新鲜；其余 `traffic-light-*` 一律视为旧格式删除。
- 文件：`.pid`/`.cbpid` 一律删；`.state` 后缀非纯数字视为旧格式删；`.bind` **不能套"非数字即旧"规则**（后缀是 uuid），只按 pid+创建时间判存活；`.win` 超过阈值未刷新视为孤儿删。
- GC 在安装脚本与每次 SessionStart 各跑一次，幂等。

### Hook 契约

- SessionStart → 解析 + 写绑定 + 抢窗/拉灯 + GC。
- UserPromptSubmit → thinking；顺带做 TTL 检查与自愈。
- PostToolUse → running/failure；只读绑定 + 写状态，零额外进程。
- Notification(permission_prompt) → waiting。
- Stop → success（保留 `/clear` 的 idle 防抖）。
- SessionEnd → ended（不删文件、不杀进程）。

## Testing Decisions

好的测试只验证外部可观察行为：给定一组绑定/状态文件与一份进程快照，断言"哪盏灯、什么状态、标签是什么"，不断言内部函数调用顺序。

三个 seam，按优先级：

1. **状态源到聚合（最高 seam，Python）**：把"扫绑定 ⋈ 读状态 → 按 hwnd 过滤 → 按 pid 聚合 → 输出状态与标签"整段作为一个 seam 测试，沿用现有内存状态源做替身。覆盖：同 cwd 双 pid 互不覆盖；`ended` 且活 pid 按 idle；`·N` 按 distinct pid；跨项目聚合的标签选择；TTL 淘汰。
2. **解析决策函数（PowerShell，快照注入）**：解析器接受"进程快照 + 绑定/垃圾文件目录"作为输入，输出 JSON 决策（pid、hwnd、degraded、claim、gc 动作）。单测只喂快照与文件树，不碰真实进程与窗口。覆盖：进程树认领、父进程创建时间倒挂拒绝、PID 转世拒绝、GC 三类规则（新/旧格式任务、旧 state、绑定存活）。
3. **手工验收（机器相关，不进单测）**：`probe.ps1` 在两个终端各跑一次，VERDICT 的 hwnd 必须不同（相同则命中同窗聚合）；两条底线——两个终端各自只有自己的灯；`taskkill /F` 一个终端后另一盏无恙、死灯一个 tick 内自灭且计划任务消失。另加 `/clear` 不闪不重建。

单测的既有先例是现有的状态管理与生命周期测试（内存替身 + 纯逻辑断言）。

## Out of Scope

- Agent / 子代理维度的状态区分（目标是一终端一灯，agent 并行不是本次驱动）。
- 灯上显示 git 分支名等"分得清是谁"的增强（后续阶段）。
- mintty / VSCode 集成终端的完整支持（降级 `?` 兜底，写进支持矩阵）。
- 保留项目级聚合灯或新旧键并存。
- 跨机器/网络同步。
- 灯的外观、动画、尺寸调整。

## Further Notes

- 探针在本机 WT/ConPTY 上已验证：attach 到 CodeBuddy 进程得到 `PseudoConsoleWindow`，`GW_OWNER` 指向 `CASCADIA_HOSTING_WINDOW_CLASS` 的 1199×616 窗口；同时确认沿父链上溯一个可绑定窗口都拿不到（窗口属于 conhost 子进程，不属于 cmd）。因此"只靠父链取窗口"的方案不可行。
- Windows Terminal 同一个进程里，窗口句柄关掉后可能被新窗口复用，且 owner 的 pid+创建时间完全相同 —— owner 二元组对 WT 天然不够，必须靠"nonce + 锚心跳 + 本窗还有没有活绑定"三件套；owner 二元组降为次级校验。
- WT 窗口标题就是当前标签标题、也是对话标题，后续做"分得清"时可白捡，不用 UI Automation。
- `schtasks /TR` 有 261 字符上限，drawer 的状态目录与锚路径必须由自身位置推导，命令行只传 hwnd 与 nonce。
- 两台机器上的用户执行策略大概率是 Restricted，所有 ps1 调用统一 `-NoProfile -ExecutionPolicy Bypass`；漏一处即静默失效。
- 发布包必须包含解析脚本，否则 EXE 用户灯全灭。
- 小概率但需接受：解析失败期间该会话无窗可贴，只能出现在降级灯上，直到下一条提示重新解析成功。
